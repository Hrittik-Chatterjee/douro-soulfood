# i18n: D'ouro Soulfood

**de-AT is the only live locale.** This document describes real, shipped infrastructure — not a plan for infrastructure that doesn't exist yet.

## The one gate: `LIVE_LOCALES`

`src/lib/i18n/locales.ts` holds `LOCALE_REGISTRY` (every locale this site knows about — `de-AT` live, `en`/`zh`/`pt` `planned` with a `blockedBy` reason) and derives `LIVE_LOCALES` from it. Everything else in this document reads `LIVE_LOCALES`, never the full registry, for anything that could produce a URL, a link, or a rendered string. A locale becomes live by changing its `status` in one file — nothing else needs to change for the gates below to start behaving differently.

**Why `en`/`zh`/`pt` are `planned`, not live:** the only non-German content in the repo is `descriptionEn` on 39 of 43 menu items. No page prose, no translated FAQ, no zh/pt content in any form exists. Machine translation is explicitly excluded — shipping it would violate this project's own non-negotiables ("no generic AI filler copy") and Google's guidance on scaled AI content. A locale activates only when real human translation exists for it.

## What's actually wired

- **`astro.config.mjs`**: `i18n.locales` = `[...LIVE_LOCALES]` (currently `['de-AT']`), `routing.prefixDefaultLocale: false` (German stays at `/`, `/menu` — zero URL churn when this was added), no `fallback` set. The sitemap integration's `i18n.locales` map is built the same way, from `LIVE_LOCALES`.
- **Provable today**: `grep -c 'xhtml:link' dist/client/sitemap-0.xml` = `0`. No `hreflang` anywhere in the built HTML. Verified against the installed `@astrojs/sitemap@3.7.2` source (`generate-sitemap.js`): its own `if (links.length <= 1) return void 0` guard means a locale map with one entry can only ever produce one link per path, so alternates self-suppress structurally — not because anything is disabled, because there's nothing to pair with yet.
- **`src/lib/nav.ts`**: the primary 4-item nav, defined once and consumed by `NavBar.astro` (and, through it, `MobileNavDrawer.astro`, which receives `links` as a prop) and `Footer.astro`. "Catering" (NavBar) vs "Catering & Events" (Footer) is a genuine pre-existing content difference, kept as an explicit override (`FOOTER_NAV_LINKS`) rather than silently collapsed — which wording is correct is a copy decision, not a code one.
- **`src/lib/i18n/ui.ts` + `messages/de-AT.ts`**: a small dictionary for chrome strings that must not live in Keystatic (a client editing CMS copy must not be able to break an `aria-label` or the string a script keys off of). German is the `UIKey` type source; `t(key, locale)` falls back to German for any locale that doesn't have the key, never a raw key. Currently covers the mobile nav drawer's open/close `aria-label`s, which used to be hardcoded literals inside `MobileNavDrawer.astro`'s inline `<script>` (`btn.setAttribute('aria-label', 'Navigationsmenü öffnen')`) — that string is now rendered server-side into `data-label-open`/`data-label-close` on the button, and the script reads the data attribute instead of hardcoding the word. Two paired reasons this matters: a hardcoded literal there would silently render German on a future English page, and it would cost the CSP-hash-pinned script a new hash per locale, since its bytes would then differ by language.
- **`src/lib/i18n/content.ts`**: `localized(entry, field, locale)` resolves a locale-suffixed CMS field (`description` → `descriptionEn` for `en`) without any consumer naming the storage field. Not yet called from any live page — de-AT is the only locale, so every call would resolve to the base field regardless. It exists so wiring a locale-aware menu page in Phase 3 is a change to call sites, not a new accessor design.
- **`LanguageSwitcher.astro`**: renders nothing while `LIVE_LOCALES.length < 2`. Not currently mounted in any layout — mounting a component that unconditionally renders nothing would be dead weight in the DOM for zero benefit today. Phase 3 imports and places it once a second locale goes live; the component's own guard means no call site ever needs to re-check locale count.
- **`scripts/checks/verify-i18n.mjs`** (`pnpm check:i18n`): fails the build if a `LIVE_LOCALES` entry other than the default doesn't have a `src/lib/i18n/messages/<locale>.ts` file with 100% `UIKey` coverage, and if the registry itself has structural problems (duplicate codes, a default that isn't live). Verified fail-closed: temporarily marking `en` live without a dictionary file produces exit code 1 and a precise "missing N/M keys" or "file does not exist" message, not a silent pass.

## What's deliberately NOT wired

- **No `src/pages/en/`, `zh/`, or `pt/` directory.** Declaring a locale live with no pages for it is exactly the state `verify-i18n.mjs` and the `astro.config.mjs` comment both warn against.
- **No `i18n.fallback`.** Setting one would make Astro serve German content at `/en/*` paths that look translated but aren't — worse than a 404.
- **Legal pages stay German-only, permanently — this is a business decision, not a gap.** `/impressum` and `/datenschutz` never get a locale sibling and never claim an `hreflang` alternate: German is legally authoritative for both (§5 ECG, §25 MedienG, GewO 1994, DSGVO/DSG). Because alternates are computed per path (see the sitemap `i18n` wiring above), these two pages structurally cannot claim one — there is no `/en/impressum` for the sitemap to pair them with, by design, not by oversight.
- **`LanguageSwitcher` is not mounted anywhere yet** — see above.

## Phase 3 entry criteria (English), not started

Per the original rollout plan: 100% `en` key coverage in `messages/en.ts` (enforced automatically once `en` is added to `LIVE_LOCALES` — that's the point of `verify-i18n.mjs`), 4/4 FAQ entries translated (needs optional `questionEn`/`answerEn` added to **both** `content.config.ts` and `keystatic.config.ts` — those two files are hand-synced, not generated, per `CLAUDE.md`), 43/43 `descriptionEn` (39 today), and hand-translated prose for the 5 non-legal pages. Then: extract page bodies so English pages don't duplicate ~2,200 words of layout code, add `src/pages/en/*.astro` (deliberately **no** `en/impressum`, **no** `en/datenschutz`), add `'en'` to `LIVE_LOCALES`, mount `LanguageSwitcher`, add `tests/en/*.spec.ts`, and update `.lighthouserc.cjs` + any Lighthouse-audited URL list together.

## Verify against official sources before extending this (do not guess)

`Astro.currentLocale` behavior on unprefixed routes under `prefixDefaultLocale:false` when a second locale is added; `getRelativeLocaleUrl`/`getAbsoluteLocaleUrlList` trailing-slash behavior; whether `@astrojs/sitemap`'s `i18n.locales` map and `serialize` hook still behave as verified here on whatever version is installed at the time — re-verify against the installed source, don't trust this document's version-pinned claims once the dependency has moved.
